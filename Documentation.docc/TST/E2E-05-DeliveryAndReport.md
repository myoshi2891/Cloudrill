## 1. シナリオと観点

コンテンツの担当者がパックをリリースし、利用者の端末に届く。利用者が誤りを報告し、担当者に届く。この 2 つの流れを、ステージングの環境と実機で通す。

- **配信**: リリース → 端末での確認 → 取得 → 検証 → 反映。反映のタイミング(受験中は反映しない)。
- **拒否**: 改ざんしたパック、アプリの版が足りないパック、古い版。
- **通信の状態**: 取得の途中での切断、機内モード、復帰。
- **報告**: オフラインでの保存、復帰後の送信、サーバーでの保存と置き換え。

この確認項目書の項目は、配信基盤と report-api がまだないため、すべて P5 以降に実施する。DDD-P5 P5-S08 の検証手順を、項目として展開したものである。セキュリティの観点は [SEC-08](../SEC/SEC-08-DeliveryInfra.md) と [SEC-07](../SEC/SEC-07-ErrorReport.md) で扱う。

## 3. 既存のテストで覆われていない点

- 全項目が未実施で、対象も未実装である。
- 結合テストで先に確認できる部分は、IT-05 に挙げた(Fake の CDN を使う差分更新、report-api の契約)。E2E では、実際の CDN・実機・実際の通信でしか確認できないこと(キャッシュの効き方、バックグラウンドからの復帰、App Attest)を見る。
- App Attest は実機でしか動かない。シミュレータでは報告の送信を確認できない。
